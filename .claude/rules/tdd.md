# TDD Rule

> **경고: 이 규칙은 Rigid다.** 상황에 맞게 변형하지 마라. 예외를 두고 싶다는 생각이 들면, 그 생각 자체가 "변명 차단표" 대상이다.

## 0. 우선순위

이 파일은 **기본값(fallback)**이다. 프로젝트 루트 또는 하위 디렉토리의 `CLAUDE.md`/`AGENTS.md`에 TDD 관련 규칙이 명시되어 있으면 **그 규칙이 이 파일보다 우선**한다. 충돌이 없는 부분은 이 파일의 기준을 그대로 따른다.

## 1. 적용 기준

### TDD를 반드시 적용해야 하는 대상

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이)
- **API 핸들러/엔드포인트** (요청 검증, 응답 형태, 에러 처리 포함)
- **유틸리티/순수 함수**
- **버그 수정** (재현 테스트 없이 수정 금지)

### TDD가 불필요한 대상

- **타입 정의** (interface, type alias)
- **설정 파일** (config, env, build 스크립트)
- **순수 UI 컴포넌트** (로직 없이 마크업/스타일만 렌더링)
- **SQL/마이그레이션 스크립트**

판단이 애매한 대상(예: 로직이 섞인 UI 컴포넌트)은 로직 부분만 분리해 테스트하고, 렌더링 자체는 적용 대상에서 제외한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 몰아넣지 않는다.
- 테스트를 작성한 즉시 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 테스트는 없는 것과 같다.
- 실패 이유는 반드시 **"기능 미구현"**이어야 한다. 문법 오류, import 누락, 타입 오류로 인한 실패는 RED가 아니다 — 먼저 고쳐서 "기능이 없어서 실패"하는 상태로 만든다.

### GREEN

- **테스트를 통과시키는 최소한의 코드만** 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 기능, 파라미터, 분기를 추가하지 않는다.
- 코드를 작성한 뒤 **신규 테스트와 기존 테스트 전부** 통과하는지 확인한다. 일부만 돌려보고 넘어가지 않는다.

### REFACTOR

- 이 단계에서 할 수 있는 것: **중복 제거, 이름 개선, 헬퍼 추출**.
- **green을 유지**한 채로만 진행한다. 리팩토링 중 테스트가 깨지면 즉시 되돌린다.
- **새로운 동작을 추가하지 않는다.** 리팩토링 중 "이것도 되면 좋겠다"는 생각이 들면 그것은 다음 사이클의 RED다.

### 반복

REFACTOR가 끝나면 다음 동작에 대한 **RED로 돌아간다.** 사이클을 건너뛰지 않는다.

## 3. 삭제 강제 규칙

- **테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작한다.**
- "일단 짜둔 거 지우기 아까우니 참고용으로 남긴다" — **금지.** 주석 처리, 별도 파일 보관, `_old` 접미사 등 어떤 형태로도 남기지 않는다.
- 예외 없음. 코드 한 줄이든 전체 함수든 동일하게 적용한다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드일수록 테스트 작성 비용이 거의 0에 가깝다. 단순하다는 이유로 생략하면, 정작 단순함이 깨지는 변경(리팩토링, 확장) 시점에 안전망이 없다. |
| "나중에 추가하겠다" | "나중"은 오지 않는다. 테스트 없는 코드는 이미 배포/머지되는 순간 "완료"로 취급되고, 이후 테스트를 추가할 유인이 사라진다. |
| "시간이 없다" | 테스트 없이 짠 코드는 디버깅·회귀 확인에 더 많은 시간을 쓴다. TDD는 시간을 아끼는 방법이지 쓰는 방법이 아니다. |
| "삭제하면 낭비" | 검증되지 않은 코드는 자산이 아니라 부채다. 테스트 없이 존재한다는 것 자체가 신뢰할 수 없다는 뜻이며, 남겨두면 나중에 "이거 왜 있지"로 돌아온다. |
| "프로토타입이다" | 프로토타입은 반드시 버려지거나, 반드시 프로덕션이 된다. 버려질 것이면 애초에 이 규칙 대상이 아니고, 프로덕션이 될 것이면 지금부터 TDD를 적용하는 게 나중에 다시 짜는 것보다 싸다. |
